## Introduction

This document establishes guardrails and best practices for AI-assisted code generation ("vibe coding") in the NumberSense project. These guidelines ensure that code generated by AI agents is safe, maintainable, and consistent with our architectural standards.

### Why This Matters

AI coding assistants can dramatically accelerate development, but without proper guardrails they can introduce:
- Non-existent APIs and hallucinated library methods
- Inconsistent architectural patterns
- Duplicate or conflicting implementations
- Security vulnerabilities
- Untestable code
- Accessibility issues (critical for educational software)

### Core Principles

1. **Trust but Verify** - AI suggestions require human validation
2. **Single Source of Truth** - One canonical location for every definition
3. **Fail Fast** - Automated checks catch issues before merge
4. **Documentation First** - Interfaces documented before implementation
5. **Incremental Validation** - Small, verifiable changes over large refactors

## 1. Safe Parallelization of Agent-Based Coding

### 1.1 Module Boundary Definitions

When multiple agents work simultaneously, strict module boundaries prevent collisions.

#### Directory Ownership Model

```
src/
├── frontend/           # Agent A: UI Components
│   ├── components/     # React components only
│   ├── hooks/          # Custom React hooks
│   ├── pages/          # Page-level components
│   └── styles/         # Component styles
├── backend/            # Agent B: API Services
│   ├── routes/         # HTTP route handlers
│   ├── services/       # Business logic
│   ├── middleware/     # Express middleware
│   └── db/             # Database operations
├── shared/             # Agent C: Shared Contracts (LOCKED)
│   ├── types/          # TypeScript interfaces
│   ├── constants/      # Application constants
│   ├── schemas/        # Validation schemas
│   └── utils/          # Pure utility functions
```

#### Rules for Parallel Work

| Rule | Description |
|------|-------------|
| **Exclusive Ownership** | Only one agent modifies files in their assigned directory |
| **Shared Directory Lock** | Changes to `/shared/` require coordination ticket |
| **Interface-First** | Shared types defined and approved before implementation |
| **No Cross-Boundary Imports** | Frontend cannot import from backend (use shared only) |

### 1.2 Preventing Merge Conflicts

#### File Locking Protocol

```yaml
# .ai-locks.yaml - Track which agent owns which files
locks:
  - path: "src/frontend/components/MathProblem/**"
    agent: "agent-frontend-1"
    expires: "2026-01-24T18:00:00Z"
    task: "TASK-123: Create MathProblem component"

  - path: "src/backend/services/scoring/**"
    agent: "agent-backend-1"
    expires: "2026-01-24T18:00:00Z"
    task: "TASK-124: Implement scoring service"
```

#### Branch Strategy

```
main
├── feature/frontend-math-problem    # Agent A
├── feature/backend-scoring          # Agent B
└── feature/shared-types-v2          # Requires approval before merge
```

### 1.3 Communication Protocols Between Agents

#### Contract Change Request (CCR)

When an agent needs to modify shared interfaces:

```typescript
// CCR-001: Add studentAge to User interface
// Requested by: agent-backend-1
// Reason: Age-based difficulty scaling
// Impact: Frontend components using User type

interface User {
  id: string;
  name: string;
  // PROPOSED ADDITION:
  studentAge?: number;  // Optional for backward compatibility
}
```

#### Coordination Points

1. **Before Starting Work**
   - Check `.ai-locks.yaml` for conflicts
   - Claim files being modified
   - Document the scope in task description

2. **During Work**
   - Stay within claimed boundaries
   - Create stub implementations for cross-boundary dependencies
   - Document assumptions about external interfaces

3. **Before Merging**
   - Release file locks
   - Verify no conflicting changes in target branch
   - Run full integration test suite

## 2. Preventing Hallucinated APIs

### 2.1 The Hallucination Problem

AI models may generate code using:
- Non-existent library methods
- Deprecated API signatures
- Incorrect parameter types
- Made-up package names

### 2.2 Validation Techniques

#### Technique 1: TypeScript Strict Mode

```json
// tsconfig.json
{
  "compilerOptions": {
    "strict": true,
    "noImplicitAny": true,
    "strictNullChecks": true,
    "noUncheckedIndexedAccess": true,
    "exactOptionalPropertyTypes": true
  }
}
```

#### Technique 2: Import Validation Script

```bash
#!/bin/bash
# scripts/validate-imports.sh

echo "Validating all imports resolve correctly..."

# Check that all imports can be resolved
npx tsc --noEmit --skipLibCheck false

# Verify no dynamic requires of non-existent modules
npx eslint --rule 'import/no-unresolved: error' src/
```

#### Technique 3: API Existence Verification

Before using any library method, verify it exists:

```typescript
// BAD: AI might hallucinate this method
const result = someLibrary.processDataAdvanced(input);

// GOOD: Verify method exists at runtime in development
if (process.env.NODE_ENV === 'development') {
  if (typeof someLibrary.processDataAdvanced !== 'function') {
    throw new Error('API verification failed: processDataAdvanced does not exist');
  }
}
const result = someLibrary.processDataAdvanced(input);
```

### 2.3 Documentation-First Development

#### Step 1: Define Interface Before Implementation

```typescript
// src/shared/types/scoring.ts
/**
 * Scoring service interface - APPROVED
 * @see ADR-005 for design decisions
 */
export interface ScoringService {
  /**
   * Calculate score for a completed problem
   * @param answer - The student's answer
   * @param expected - The correct answer
   * @param timeSpent - Milliseconds spent on problem
   * @returns Score between 0-100
   */
  calculateScore(answer: number, expected: number, timeSpent: number): number;

  /**
   * Get difficulty adjustment based on recent performance
   * @param studentId - The student's unique identifier
   * @param recentScores - Last N scores
   * @returns Difficulty multiplier (0.5 to 2.0)
   */
  getDifficultyAdjustment(studentId: string, recentScores: number[]): number;
}
```

#### Step 2: AI Implements Against Interface

The AI agent receives the interface and implements only the defined methods.

## 3. Validating Library Usage

### 3.1 Pre-Use Verification Checklist

Before AI uses any library, verify:

- [ ] Package exists on npm/registry
- [ ] Package is actively maintained (commits in last 6 months)
- [ ] Package has acceptable license (MIT, Apache 2.0, BSD)
- [ ] API being used exists in the pinned version
- [ ] No known security vulnerabilities (npm audit)

### 3.2 Approved Library Registry

Maintain a list of pre-approved libraries:

```yaml
# .approved-libraries.yaml
libraries:
  react:
    version: "18.2.0"
    license: "MIT"
    approved_date: "2026-01-01"
    approved_by: "tech-lead"
    usage: "UI framework"

  zod:
    version: "3.22.4"
    license: "MIT"
    approved_date: "2026-01-01"
    approved_by: "tech-lead"
    usage: "Runtime validation"

  # Libraries NOT approved
  blocked:
    - name: "moment"
      reason: "Use date-fns instead - moment is deprecated"
    - name: "lodash"
      reason: "Use native JS methods or lodash-es for tree shaking"
```

### 3.3 Deprecation Detection

```typescript
// scripts/check-deprecations.ts
import { execSync } from 'child_process';

const DEPRECATION_PATTERNS = [
  'componentWillMount',
  'componentWillReceiveProps',
  'componentWillUpdate',
  'findDOMNode',
  'ReactDOM.render',  // Use createRoot in React 18
];

function checkForDeprecations() {
  for (const pattern of DEPRECATION_PATTERNS) {
    const result = execSync(
      `grep -r "${pattern}" src/ --include="*.tsx" --include="*.ts" || true`,
      { encoding: 'utf-8' }
    );
    if (result.trim()) {
      console.error(`DEPRECATED API FOUND: ${pattern}`);
      console.error(result);
      process.exit(1);
    }
  }
}
```

## 4. Preventing Architectural Drift

### 4.1 Architecture Decision Records (ADRs)

Every significant decision must be documented:

```markdown
# ADR-001: Use React for Frontend

## Status
Accepted

## Context
Need to choose a frontend framework for the K-3 math education app.

## Decision
Use React 18 with TypeScript for the frontend.

## Consequences
- Positive: Large ecosystem, good TypeScript support
- Positive: Concurrent rendering for smooth animations
- Negative: Learning curve for new developers
- Negative: Need additional state management solution

## AI Agent Instructions
- Use functional components with hooks
- Do NOT use class components
- Use React Query for server state
- Use Zustand for client state
```

### 4.2 Pattern Library

Define approved patterns that AI agents must follow:

#### Component Pattern

```typescript
// APPROVED PATTERN: Functional component with props interface
interface MathProblemProps {
  problem: Problem;
  onAnswer: (answer: number) => void;
  difficulty: DifficultyLevel;
}

export function MathProblem({ problem, onAnswer, difficulty }: MathProblemProps) {
  // Implementation
}

// FORBIDDEN: Default exports, class components, any types
```

#### Service Pattern

```typescript
// APPROVED PATTERN: Dependency injection with interfaces
export function createScoringService(
  repository: ScoreRepository,
  config: ScoringConfig
): ScoringService {
  return {
    calculateScore(answer, expected, timeSpent) {
      // Implementation
    },
    getDifficultyAdjustment(studentId, recentScores) {
      // Implementation
    }
  };
}
```

### 4.3 ESLint Rules for Consistency

```javascript
// .eslintrc.js
module.exports = {
```

## 5. Maintaining Single Source of Truth

### 5.1 Shared Type Definitions

All types used across boundaries live in one place:

```
src/shared/types/
├── index.ts           # Re-exports all types
├── user.ts            # User-related types
├── problem.ts         # Math problem types
├── scoring.ts         # Scoring types
├── api.ts             # API request/response types
└── events.ts          # Event payload types
```

#### Rules for Shared Types

1. **No Duplication** - If a type exists in shared, use it
2. **Backward Compatible** - New fields must be optional or have defaults
3. **Versioned Changes** - Breaking changes require version bump
4. **Generated from Schema** - API types generated from OpenAPI/JSON Schema

### 5.2 Configuration Management

```typescript
// src/shared/config/index.ts
export const CONFIG = {
  // Environment-specific values loaded at runtime
  apiUrl: process.env.VITE_API_URL,

  // Static configuration - SINGLE SOURCE OF TRUTH
  scoring: {
    maxScore: 100,
    timeBonus: {
      threshold: 5000, // ms
      bonus: 10
    },
    streakMultiplier: 1.5
  },

  difficulty: {
    levels: ['easy', 'medium', 'hard'] as const,
    default: 'easy' as const
  }
} as const;

export type DifficultyLevel = typeof CONFIG.difficulty.levels[number];
```

### 5.3 Constants and Enums

```typescript
// src/shared/constants/index.ts

// Use const objects with 'as const' for type inference
export const PROBLEM_TYPES = {
  ADDITION: 'addition',

export const ERROR_CODES = {
```

## 7. Testing Strategies for AI-Generated Code

### 7.1 Test-Driven Development with AI

#### Workflow

1. **Human writes test specification**
```typescript
// tests/scoring.spec.ts
describe('ScoringService', () => {
  it('should return 100 for correct answer within time bonus threshold', () => {
    // AI implements to make this pass
  });

  it('should apply streak multiplier for consecutive correct answers', () => {
    // AI implements to make this pass
  });

  it('should return 0 for incorrect answer', () => {
    // AI implements to make this pass
  });
});
```

2. **AI implements code to pass tests**
3. **Human reviews implementation**

### 7.2 Required Test Types

| Test Type | Requirement | Purpose |
|-----------|-------------|---------|
| Unit Tests | 80% coverage | Verify individual functions |
| Integration Tests | All API endpoints | Verify component interaction |
| E2E Tests | Critical paths | Verify user workflows |
| Accessibility Tests | All components | WCAG 2.1 AA compliance |
| Snapshot Tests | UI components | Catch unintended changes |

### 7.3 Property-Based Testing

For math operations, use property-based testing:

```typescript
import { fc } from '@fast-check/vitest';

describe('Addition Problems', () => {
  it('should always produce correct expected answer', () => {
    fc.assert(
      fc.property(
        fc.integer({ min: 0, max: 20 }),
        fc.integer({ min: 0, max: 20 }),
        (a, b) => {
          const problem = generateAdditionProblem(a, b);
          return problem.expected === a + b;
        }
      )
    );
  });

  it('should never produce negative numbers for K-3', () => {
    fc.assert(
      fc.property(
        fc.integer({ min: 0, max: 20 }),
        fc.integer({ min: 0, max: 20 }),
        (a, b) => {
          const problem = generateSubtractionProblem(a, b);
          return problem.expected >= 0;
        }
      )
    );
  });
});
```

### 7.4 Snapshot Testing Guidelines

```typescript
// Use snapshots for UI structure, not for logic
describe('MathProblem Component', () => {
  it('should match snapshot for addition problem', () => {
```

### A.4 Emergency Procedures

#### Discovered Hallucinated API in Production

1. **Immediate**: Revert the PR
2. **Investigate**: Identify all usages
3. **Fix**: Replace with real API or implement correctly
4. **Prevent**: Add to deprecation/forbidden list
5. **Document**: Create incident report

#### Security Vulnerability in AI-Generated Code

1. **Immediate**: Disable affected feature if critical
2. **Assess**: Determine exposure and impact
3. **Patch**: Fix vulnerability
4. **Audit**: Review similar AI-generated code
5. **Update**: Add checks to prevent recurrence
